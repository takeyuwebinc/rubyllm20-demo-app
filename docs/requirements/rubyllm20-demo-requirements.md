# RubyLLM 2.0 新機能デモアプリ 要件定義書

## 1. 機能概要

RubyLLM 2.0 の新機能 10 個を理解するためのデモアプリである。機能ごとに 1 つのデモを用意し、その機能がどんなケースで役立つかの説明と、実際のプロバイダーに対して実行できる代表シナリオを提供する。特定の案件を前提とせず、RubyLLM 2.0 で何ができるようになったかを体系的に知ることを目的とする。

対象の 10 機能は次のとおり。機能名は依頼の原文に従う。RubyLLM の公式ドキュメントでの名称が異なるものは、5. 用語定義に対応を示す。

- Responses API
- Citations
- Tool Approval
- Batches
- Model Fallbacks
- Video and Speech Generation
- Provider Tools
- Deep Research
- Tokenization and Token Counting
- Workflow Instrumentation

**主要な提供価値**：
- 10 機能それぞれについて、役立つケースの説明と、実際のプロバイダーでの実行結果を同じデモで得られる
- 実行しているコードの断片を、自分の案件で書き直すときの参考にできる
- 利用者の指定により、試行ごとの観察情報を Sentry で確認できる。F1、F5、F10 では、これが機能の働きを確かめる手段になる

### 1.1 当初の目的

依頼の原文は次のとおり。

> RubyLLM 2.0 の以下に挙げた新機能を理解するためのデモアプリを検討する。デモでは各機能がどんなケースで役立つか説明する形で実装することを前提に、検討を進めよ。

- **課題**：特定の案件はない。RubyLLM 2.0 で何ができるようになったかを体系的に知っておきたい。
- **理想の状態**：10 機能それぞれについて、どんなケースで役立つかを理解している。
- **成功基準**：定性的な基準のみ。
  - ① 各機能について、使うべき場面と使うべきでない場面を自分の言葉で説明できる。
  - ② デモのコードを、自分の案件に持ち込む出発点として使える。粒度は、画面上のコード断片を参考に自分で書き直せれば足りる。

成功基準①は、要求分析の過程で次のとおり変更した。

- **変更後の成功基準①**：各機能について、使うべき場面を自分の言葉で説明できる。
- **変更の理由**：当初の依頼は「各機能がどんなケースで役立つか説明する」であり、使うべきでない場面の説明は含まれていないため、当初の依頼の範囲に合わせる。

成功基準の達成は、利用者の自己判定による。

### 1.2 目的の達成範囲

- **判定**：条件付き達成（変更後の成功基準に対する判定）
- **目的と要件の対応**：

| 目的の単位 | 寄与する要件（優先度） | 評価 |
|-----------|---------------------|------|
| G1. 10 機能を体系的に知る | C1、C8、C9、F1〜F5、F6a、F6b、F7a、F8、F9a、F9b、F10（すべて Must） | Must で満たされる |
| G2. 各機能について、使うべき場面を説明できる | C2、C3、C5、C7、C8、C9、F1〜F5、F6a、F6b、F7a、F8、F9a、F9b、F10（すべて Must） | Must で満たされる。F8 の実行だけは、下の条件による |
| G3. 画面上のコード断片を参考に、自分で書き直せる | C4（Must） | Must で満たされる |

- **判定の根拠**：
  - Batches を使うべき場面を説明しようとする場面をたどった。C1 の一覧から Batches のデモに入ると、C2 の説明、C5 の実行結果、C4 のコード断片が得られる。結果は後から届くが、C9 と C8 により履歴で受け取れる。
  - 外部への依存が最も強い F8 もたどった。F8 の実行は、Vertex AI が Preview として提供する Deep Research エージェントを利用できることに依存する。C2、C3、C4 の説明、公式ドキュメント、コード断片は、この条件によらず得られる。
- **要件の外にある条件**：

| 条件 | 引き受け手 | 時期 | 満たされない場合 |
|------|-----------|------|----------------|
| Vertex AI の Deep Research エージェントでジョブを投入できること。2026-09-19 時点では、投入が Vertex AI のクォータ（Stateful Interaction Creation requests per minute per project）の超過として拒否され、実行できない | 利用者本人。Google Cloud でクォータを申請する | F8 の実装に着手する前 | F8 のデモは、説明文とコード断片のみとする |

- **改善の履歴**：
  - 1 回目の判定は未達だった。当初の成功基準①に含まれる「使うべきでない場面を説明できる」に寄与する要件がなかった。
  - 改善として、利用者は「目的を見直す」を選び、成功基準①を「使うべき場面を説明できる」に狭めた。要件は追加していない。
  - 2 回目の判定で達成とした。
  - 文書だけを入力にした独立の判定では、F8 が Preview の提供に依存し、その条件の引き受け手が書かれていないため、条件付き達成となった。利用者は、Deep Research の実際のジョブで利用の可否を確認することを選んだ。
  - 確認では、間隔を空けた 3 回の投入が、いずれもクォータの超過として拒否された。利用者は、クォータの申請を引き受け、判定を条件付き達成とすることを選んだ。
- **補足**：
  - C7（観察情報）は利用者が Must と指定した要件である。F1、F5、F10 の確認手段を兼ねる。
  - C10（エラーの表示）は、目的の単位に直接は寄与しない。API 費用の上限を設けないため、残高の不足で実行が止まることがあり、その原因を利用者が切り分けて実行を続けるための要件である。
  - F7b は Should である。Provider Tools の理解は F7a（Must）で成立する。

## 2. 機能要件

操作者は、すべての要件で利用者（開発者本人）である。

### 2.1 基本処理フロー

1. **デモを選ぶ**
   - 利用者は、10 機能の一覧から理解したい機能のデモを選ぶ。
   - 一覧で、機能ごとの役立つケースの要約と、実行できる状態かどうかが分かる。

2. **説明を読む**
   - 利用者は、デモの画面で、その機能が役立つケース、その機能を使わない場合に困ること、実行しているコードの断片を読む。
   - 説明文から、根拠とした公式ドキュメントへ移動できる。

3. **代表シナリオを実行する**
   - 利用者は、既定の入力で、代表シナリオを実際のプロバイダーに対して実行する。C6 を実装した場合は、入力を変更して実行できる。
   - 結果がすぐに得られる機能では、実行後に結果が表示される。
   - 結果が後から届く機能では、実行中の状態が表示され、結果は履歴に届く。
   - 利用者の承認を待つ機能では、承認待ちの状態が表示され、利用者が承認または却下を行うと続きが実行される。
   - 実行が失敗した場合は、エラーの内容と原因の手がかりが表示される。

4. **結果を見返し、観察情報を確認する**
   - 利用者は、履歴から過去の実行の入力、結果、状態を見返す。
   - 利用者は、履歴から、その実行に属する Sentry のトレースへ移動し、試行ごとの観察情報と、プロンプトと応答の本文を確認する。

### 2.2 共通要件

| # | 要件 | 理由 | 優先度 |
|---|------|------|--------|
| C1 | 10 機能を一覧できる。一覧から各デモへ移動でき、機能ごとに、役立つケースの要約と、実行できる状態かどうか（必要な設定値が存在するか）が分かる。設定値が有効かどうかは、実行時のエラー（C10）で分かる | 10 機能を体系的に把握するため | Must |
| C2 | 各デモで、その機能が役立つケースと、その機能を使わない場合に困ることを、説明文で読める。使わない場合に困ることには、その機能なしで同じ目的を果たそうとしたときに必要になる手間と、起こる問題を書く。機能の制約と、使うべきでない場面は書かない。使わない場合の処理は実行しない | 当初の依頼が「どんなケースで役立つか説明する形」であるため | Must |
| C3 | 各デモの説明文から、根拠とした RubyLLM の公式ドキュメントへ移動できる。プロバイダーの仕様に基づく説明では、プロバイダーの公式ドキュメントも含める | 説明文は学習の根拠になるため、利用者が誤りを自分で確かめられるようにする | Must |
| C4 | 各デモで、代表シナリオが実行しているコードの断片を読める | 成功基準②のため | Must |
| C5 | 各デモの代表シナリオを、既定の入力で、実際のプロバイダーに対して実行できる | 説明だけでなく実際の結果を得るため | Must |
| C6 | 代表シナリオの入力を変更して再実行できる | 入力ごとの結果を履歴で見比べるため | Should |
| C7 | すべてのデモの実行について、観察情報（試行ごとのプロバイダー、モデル、トークン数、コスト、所要時間、送信先）と、プロンプトと応答の本文を、Sentry のエージェントトレーシングで確認できる。コストは RubyLLM が算出した値を用い、RubyLLM が単価を持たない操作では、コストが不明であることが分かる | 利用者の指定。F1、F5、F10 の確認手段を兼ねる | Must |
| C8 | すべての実行を履歴として保持する。履歴の一覧と、実行ごとの入力、結果、状態、実行日時を後から見返せる。結果には、生成した音声と動画を含み、履歴から再生できる。失敗した実行も残る。履歴から、その実行に属する Sentry のトレースへ移動できる | 過去の実行を見返し、結果が後から届く機能の結果を受け取るため | Must |
| C9 | 結果が後から届く機能（F4、F6b、F8）と、利用者の承認を待つ F3 では、実行の状態が分かる。利用者が画面を離れても、結果が後から届く機能の結果は履歴に届き、承認待ちの実行は履歴から承認または却下を行える。アプリの停止中にプロバイダー側の処理が完了した場合、その結果は次回の起動後に履歴へ届く | 完了までに時間がかかり、利用者が画面を開いたまま待てないため。アプリはローカルで実行するため、停止する時間帯がある | Must |
| C10 | 実行が失敗したとき、プロバイダー名、エラーの種類、プロバイダーが返したメッセージ、想定される原因の候補（認証情報、残高、権限、レート制限）を表示する | 原因がどこにあるかを利用者が切り分けるため | Must |
| C11 | 必要な設定値が存在しないデモで、認証情報の取得手順へ案内される | 認証情報がそろっていない段階でも、そろっているデモから使い始めるため | Should |

実行の状態は、実行中、承認待ち、成功、失敗、取り消しのいずれかである。プロバイダー側の処理が期限切れになった場合は失敗とし、理由が分かるようにする。取り消しは、プロバイダー側で処理が取り消された場合を指す。利用者が実行を取り消す操作は対象外とする。

### 2.3 機能別要件

デモは機能ごとに 1 つで、合計 10 個である。各デモは、架空の EC サイトのサポートデスクを舞台にした代表シナリオを持つ。F6、F7、F9 のデモは代表シナリオを 2 つ持ち、それ以外のデモは 1 つ持つ。「役立つケース」は、C2 の説明文が扱う内容である。

| # | 機能 | 役立つケース | 代表シナリオと、利用者が確認できること | 優先度 |
|---|------|-------------|--------------------------------------|--------|
| F1 | Responses API | 推論、ツール、プロバイダー側のツールを 1 回の問い合わせで扱いたい | 顧客からの問い合わせへの回答を、OpenAI のモデルに対する RubyLLM 2.0 の既定のプロトコル（Responses API）で実行する。Responses API で送信されたことを、観察情報の送信先で確認できる。このシナリオでは Web 検索を使わない | Must |
| F2 | Citations | 規約や契約のように、回答の根拠を読み手が検証する必要がある | 返品ポリシー文書に基づいて問い合わせに回答する。回答のどの部分が、文書のどの箇所とページに基づくかを確認できる | Must |
| F3 | Tool Approval | 返金、削除、送信のように取り消せない操作を AI に提案させ、実行するかどうかは人が決めたい | AI が返金を提案する。利用者が承認または却下するまで、返金は実行されない。承認すると返金が実行され、却下すると AI が却下を踏まえて応答する。承認待ちのまま利用者が画面を離れても、後から承認または却下して再開できる | Must |
| F4 | Batches | チケットの分類や要約のように、すぐに応答を返す必要がない、件数の多い処理を行いたい | 複数のサポートチケットの分類をまとめて投入し、後から結果を回収する。全体の状態と、チケットごとの成否を確認できる。コストは観察情報として確認できる | Must |
| F5 | Model Fallbacks | プロバイダーの障害やレート制限が起きても、応答を続けたい | 主モデルが応答できない状況を再現する。予備モデルで回答が得られる。結果で、応答したモデルと、切り替えの経過（失敗したモデルとエラーの種類）が分かる。失敗した試行と成功した試行は、観察情報でも確認できる。再現の手段は機能設計で決める | Must |
| F6a | Speech Generation | サポートの回答や自動音声応答の文面を読み上げたい | 回答文を音声にし、再生できる | Must |
| F6b | Video Generation | 商品の説明文から、短い紹介動画を用意したい | 商品の説明文から短い動画を生成し、完成後に再生できる | Must |
| F7a | Provider Tools（Web 検索） | 検索の仕組みを自前で構築、運用したくない | プロバイダー側の Web 検索を使い、最新の情報を含む回答を得る。行われた検索と出典を確認できる | Must |
| F7b | Provider Tools（コード実行） | コードを実行する隔離環境を自前で構築、運用したくない | プロバイダー側のコード実行を使い、注文データの集計結果を得る。実行されたコードと結果を確認できる | Should |
| F8 | Deep Research | 数分以上の待ち時間を許容して、複数の情報源にあたった調査レポートを得たい | 調査テーマを投入し、完了後にレポートと出典を読める。レポートが出典の URL を含まない場合がある | Must |
| F9a | Token Counting | 送信前に、入力がモデルの上限に収まるかを判定したい | 送信前に会話の入力トークン数を数え、モデルの上限に収まるかを確認できる | Must |
| F9b | Tokenization | テキストがトークンにどう分割されるかを知りたい | テキストがどうトークンに分割されるかを確認できる | Must |
| F10 | Workflow Instrumentation | 複数のステップからなる処理で、どのステップが時間とコストを使っているかを特定したい | チケットの分類、回答の下書き、レビューの 3 ステップからなる処理を実行する。ステップごとの所要時間、トークン数、コストを、ひとまとまりのトレースとして Sentry で確認できる | Must |

### 2.4 データ仕様

- **データソース**：すべてダミーデータである。実在の顧客、注文、個人情報は使わない。
- **データ取得要件**：代表シナリオの既定の入力は次のとおり。

| 代表シナリオ | 既定の入力 |
|-------------|-----------|
| F1 | 顧客からの問い合わせ文 |
| F2 | 顧客からの問い合わせ文と、返品ポリシー文書（ページの区別を持つ文書） |
| F3 | 返金を求める問い合わせ文と、返金の対象になるダミーの注文 |
| F4 | 複数のサポートチケット。件数は機能設計で決める |
| F5 | 顧客からの問い合わせ文 |
| F6a | 読み上げる回答文 |
| F6b | 商品の説明文 |
| F7a | 最新の情報を必要とする質問 |
| F7b | ダミーの注文データと、集計の依頼 |
| F8 | 調査テーマ |
| F9a | 指示と質問からなる会話 |
| F9b | 分割を確認するテキスト |
| F10 | サポートチケット 1 件 |

- **データ変換**：
  - F3 の返金は、ダミーの注文の状態を変えるだけで、実際の金銭は動かさない。

### 2.5 エラー処理

- **エラー条件**：
  - プロバイダーの呼び出しが失敗した：C10 のとおり表示し、履歴に失敗として残す。
  - 必要な設定値が存在しない：C1 のとおり、実行できる状態でないことを一覧で示す。C11 を実装した場合は、取得手順へ案内する。
  - 結果が後から届く機能で、プロバイダー側の処理が失敗、期限切れ、取り消しになった：履歴にその状態と理由が残る。
  - F4 で、一部のチケットだけが失敗した：チケットごとの成否が分かる。
- **エラー通知**：
  - 画面上の表示と履歴による。それ以外の通知は行わない。

### 2.6 対象外とした要求

次の要求は、利用者の判断で今回の対象外とした。

- ログイン、権限による制限、複数人での同時操作
- アプリの外部公開
- API 費用の上限を設ける仕組み
- 機能を使わない場合の処理を実際に実行して比較すること（説明文で示す）
- 1 つのデモに 3 つ以上の代表シナリオを持たせること。代表シナリオを 2 つ持つのは F6、F7、F9 のデモに限る
- 使うべきでない場面と制約の説明
- 利用者が機能ごとに自分の言葉でメモを書き残す機能
- Citations で、自前の検索ツールの結果を引用元にするシナリオ
- 観察情報をアプリ内の画面に表示すること（Sentry で確認する）
- 利用者が実行を取り消す操作

## 3. 前提条件・制約事項

### 3.1 前提条件

- **システム前提条件**：
  - 2026-09-19 時点で、OpenAI、Anthropic、xAI、Vertex AI の 4 プロバイダーとも、チャットの疎通確認が済んでいる。取得手順は `docs/api-keys.md` にある。認証情報は、失効や未設定になりうる。
  - 2026-09-19 時点で、Vertex AI の Deep Research は、ジョブの投入がクォータの超過として拒否される。認証、プロジェクト、API の有効化、ロケーションには問題がない。クォータの上限値は未確認である。
  - 利用者は sentry.io に既存の Sentry 組織を持っている。
- **データ前提条件**：
  - 2.4 のダミーデータが、アプリのセットアップ時に用意される。

### 3.2 制約事項

- **技術的制約**：
  - Rails アプリとして実装する。RubyLLM のバージョンは 2.0.0 に固定する。
  - 画面のスタイリングには Tailwind を使う。
  - テストは Minitest で書き、対象は外部の API を呼ばない部分に限る。プロバイダーの呼び出しは、実際の画面と疎通確認の手順で確かめる。
  - 認証情報と Sentry の DSN は `.env` に置く（利用者の指定）。
  - 観察情報の確認には、Sentry のエージェントトレーシングを使う（利用者の指定）。
  - 計装は OpenTelemetry で行い、Sentry へは OTLP で送る（利用者の指定）。Sentry の SDK によるトレーシングとは併用しない。
  - RubyLLM 2.0.0 に対応した既製の OpenTelemetry 計装は、2026-09-19 時点で存在しない。RubyLLM の作者による計装 gem は中身のない予告版であり、第三者による計装 gem は RubyLLM 2.0.0 でチャットの呼び出しを失敗させる。このアプリは、RubyLLM が発行する計装イベントから、自前でスパンを作る。
  - 送信先は、プロバイダーへの HTTP リクエストを表すスパンで確認する。
  - プロンプトと応答の本文は、Sentry 側では任意の項目である。このアプリでは送る。
  - Sentry の OTLP の取り込みは、2026-09-19 時点で公開ベータである。スパンイベントは取り込み時に破棄されるため、エラーの内容はスパンの属性と状態で送る。
  - Sentry が独自に推定するコストは、未知のモデル、バッチ料金、トークン課金以外の料金を対象としない。
- **業務上の制約**：
  - アプリはローカルの開発環境でのみ実行する。
  - API 費用の上限は設けない。
  - プロンプトと応答の本文を Sentry に送るため、代表シナリオの入力に、実データや個人情報を入力してはならない。
- **外部システム連携**：
  - 代表シナリオごとに使うプロバイダーは次のとおり。C1 は、この表のプロバイダーの設定値が存在するかで、実行できる状態かどうかを判定する。割り当ては、下に挙げる RubyLLM 2.0.0 の対応状況の範囲で、機能設計で見直してよい。

| 代表シナリオ | プロバイダー |
|-------------|-------------|
| F1、F3、F4、F6a、F7a、F7b、F9a、F10 | OpenAI |
| F2 | Anthropic |
| F5 | 主モデルに OpenAI、予備モデルに Anthropic |
| F6b、F9b | xAI |
| F8 | Vertex AI |

  - RubyLLM 2.0.0 の対応状況は次のとおり。
    - RubyLLM 2.0 で Responses API が既定のプロトコルになるのは、OpenAI のモデルである。音声、リアルタイム、検索用の一部のモデルは Chat Completions で送信される。
    - RubyLLM の公式ガイドが、文書に基づく Citations の対応先として挙げるのは、Anthropic、Cohere、Bedrock 上の Claude である。
    - OpenAI の動画生成 API は、2026-09-19 時点で、2026-09-24 の停止が予定されている。
    - Tokenization（テキストの分割）に対応するのは、xAI、Cohere、GPUStack である。Token Counting（会話の入力トークン数の計数）は xAI では使えず、OpenAI、Anthropic、Gemini、Bedrock、Vertex AI で使える。
    - Deep Research に対応するのは Vertex AI である。Vertex AI の Deep Research エージェントは Preview の扱いであり、ロケーションは `global` に限られる。
    - Model Fallbacks は、同一のプロバイダー内でも構成できる。このアプリでは、プロバイダーの障害を想定したシナリオにするため、予備モデルに別のプロバイダーを選ぶ。
    - Model Fallbacks が既定で切り替えの対象にするのは、レート制限、サーバーエラー、サービス停止、過負荷、タイムアウト、接続の失敗である。認証エラーやモデル名の誤りでは切り替わらない。
  - F4、F6b、F8 の完了までの時間は、プロバイダーに依存する。
  - 結果が後から届く機能では、1 回の実行が、投入と結果の回収とで複数のトレースに分かれる。

- Sentry（sentry.io）

## 4. リリース・運用要件

リリース時作業はない。定期実行の運用バッチもない。結果が後から届く機能の結果の回収は、運用作業ではなく機能要件（C9）として扱う。

### 4.1 環境構築要件

対象の環境は、ローカルの開発環境のみである。

- **環境変数・シークレット**：
  - `OPENAI_API_KEY`、`ANTHROPIC_API_KEY`、`XAI_API_KEY`、`GOOGLE_CLOUD_PROJECT`、`GOOGLE_CLOUD_LOCATION`：設定済みである。
  - Vertex AI は API キーを持たず、Google Cloud の Application Default Credentials を使う。作成済みである。失効した場合は再作成が必要になる。
  - Sentry の DSN：追加が必要である。
- **外部サービス**：
  - Sentry：既存の組織に、このデモ用のプロジェクトを追加する。トレースは OTLP で受け取る。
- **各環境セットアップ手順への影響**：
  - `docs/api-keys.md` に、Sentry のプロジェクト作成と DSN の取得手順を追記する。

## 5. 用語定義

| 用語 | 説明 |
|------|------|
| デモ | 10 機能のうち 1 つを扱う画面のまとまり。説明文、コードの断片、代表シナリオの実行からなる。合計 10 個 |
| 代表シナリオ | その機能が役立つケースを 1 つ選び、実際のプロバイダーに対して実行できるようにしたもの。F6、F7、F9 のデモは 2 つ持つ |
| 実行 | 利用者が代表シナリオを 1 回動かすこと。1 回の実行は、1 つ以上の試行を含む |
| 試行 | プロバイダーへの 1 回の送信。リトライや Model Fallbacks が起きると、1 回の実行に複数の試行が含まれる |
| ステップ | F10 で、1 回の実行を構成する名前付きの処理の単位。1 つのステップは、1 つ以上の試行を含む |
| 履歴 | 実行の記録。入力、結果、状態、実行日時を持つ |
| 状態 | 実行の状態。実行中、承認待ち、成功、失敗、取り消しのいずれか |
| 観察情報 | 試行ごとのプロバイダー、モデル、トークン数、コスト、所要時間、送信先 |
| 送信先 | プロバイダーのどの API に送信したか。F1 では、Responses API で送信されたことを確認する手がかりになる |
| プロバイダー | モデルの API を提供する事業者。このアプリでは OpenAI、Anthropic、xAI、Vertex AI |
| プロバイダー側のツール | モデルの提供者の基盤で実行されるツール。このアプリでは Web 検索とコード実行を扱う |
| サポートデスク | 代表シナリオの舞台。架空の EC サイトの顧客対応部門 |
| Tool Approval | RubyLLM の公式ドキュメントでは Human Approval for Tools |
| Deep Research | RubyLLM の公式ドキュメントでは Hosted Research |

## 1. 機能概要

### 1.1 目的

10 個のデモが共通で使う土台を用意する。対応する要件は、要件定義書の C1〜C6、C8、C10、C11 である。

- 10 機能を一覧し、デモごとの説明、出典、コード断片を読めるようにする
- 代表シナリオを実際のプロバイダーに対して実行し、すべての実行を履歴として残す
- 履歴から、その実行の観察情報を Sentry で確認できるようにする
- 土台が端から端まで動くことを確かめるため、最初の代表シナリオとして F1（Responses API）を載せる

C7（観察情報）は実装済みであり、この設計では結合先として扱う。

C9（結果が後から届く機能と、承認待ち）の仕組みは、それを使う機能の設計で扱う。この設計が C9 のために先に用意するのは、実行の状態の値（承認待ちと取り消しを含む 5 つ）だけである。プロバイダー側の処理の識別子のように、C9 が必要とする項目は、C9 を扱う設計で実行に追加する。

### 1.2 主要機能

1. **デモの一覧**: 10 機能を一覧し、機能ごとの役立つケースの要約と、実行できる状態かどうか（実行できる、設定値が足りない、準備中のいずれか）を示す
2. **デモの表示**: 説明文、出典、代表シナリオごとのコード断片と入力欄を示す
3. **代表シナリオの実行**: 実行を記録し、バックグラウンドのジョブでプロバイダーを呼び、結果か失敗の内容を実行に残す
4. **実行の表示と履歴**: 実行の入力、結果、状態、失敗の内容を示し、Sentry のトレースと会話へ移動できるようにする
5. **F1 の代表シナリオ**: 顧客からの問い合わせ文に、OpenAI のモデルで回答する

### 1.3 処理フロー概要

#### 1.3.1 デモを選んで読む

1. 利用者が一覧を開く。一覧は、デモ定義を順に並べ、デモごとに実行できる状態かどうかを示す
2. 利用者がデモを開く。デモの画面は、説明文、出典、代表シナリオを示す
3. 代表シナリオごとに、実行を担う処理のソースコードをコード断片として示し、既定の入力を入力欄に入れて示す

#### 1.3.2 代表シナリオを実行する

4. 利用者が入力を確認し、実行を指示する。入力は変更してよい
5. 実行の指示を受けた側は、その代表シナリオが実行できる状態であることと、必須の入力の項目がすべて埋まっていることを確かめる。満たさない場合は、実行を記録せず、理由を示す
6. 実行を「実行中」の状態で記録する。このとき、実行ごとの会話 ID を発行する
7. 記録が確定した後で、実行のジョブを投入する。利用者には、実行の画面を表示する
8. ジョブは、実行を読み込み、実行の会話 ID を metadata に入れて、RubyLLM の workflow を開く
9. ジョブは、workflow の内側で、現在のトレース ID を読み、実行に記録する。トレース ID が得られない場合は、記録しない
10. ジョブは、workflow の内側で、代表シナリオの処理を呼ぶ。代表シナリオの処理は、RubyLLM を呼び、結果を返す。この間に RubyLLM が発行する計装イベントは、`Observability::RubyLLMSpanSubscriber` がスパンにして Sentry へ送る
11. ジョブは、結果と終了日時を実行に記録し、状態を「成功」にする
12. プロバイダーの呼び出しが失敗した場合、ジョブは、失敗の内容と終了日時を実行に記録し、状態を「失敗」にする

workflow を開くのはジョブの責務であり、代表シナリオの処理の責務ではない。スパンは計装イベントの開始から終了までしか開かないため、トレース ID を読めるのは workflow の内側に限られる。会話 ID も、workflow の内側で発行された計装イベントにしか載らない。

#### 1.3.3 結果を見る

13. 実行の画面は、状態が「実行中」の間、実行の状態を短い間隔で取得し直して表示に反映する。状態が「実行中」でなくなったら、取得をやめる
14. 利用者は、結果か失敗の内容を読み、Sentry のトレースへ移動して観察情報を確認する
15. 利用者は、履歴の一覧から過去の実行を開き、同じ画面で見返す

## 2. 設計判断

### 2.1 採用した実装パターン

この設計では ADR を起票しない。自習用のリポジトリであり、ADR の管理サーバーに案件を立てないためである。採用案だけをここに記載し、理由は実装後にコードコメントとコミットメッセージへ移す。

| # | 判断ポイント | 採用案 | 関連ADR |
|---|------------|-------|--------|
| 1 | デモ定義と代表シナリオ定義の保持 | コードと一緒に版管理する静的な定義として持つ。DB には持たない | なし |
| 2 | 代表シナリオの実行の経路 | すべてバックグラウンドのジョブで実行する。リクエストの中では実行しない | なし |
| 3 | 開発環境のジョブの実行基盤 | Web のプロセスとは別のプロセスで動くワーカーを使う。ジョブは DB に保持する | なし |
| 4 | 実行の状態の管理 | 状態の項目を 1 つ持ち、許される遷移を実行自身が判定する。状態機械の gem は使わない | なし |
| 5 | 実行中の画面の更新 | 画面が状態を短い間隔で取得する。サーバーからの配信は使わない | なし |
| 6 | 結果の保存と表示 | 結果は構造化データで保存する。表示は、結果の種類ごとの部品に分ける | なし |
| 7 | コード断片の出どころ | 実行を担う処理のソースコードを、表示のたびに読む。説明用の写しは持たない | なし |
| 8 | Sentry との対応付け | ジョブが workflow を開き、会話 ID を metadata で渡し、workflow の内側でトレース ID を読んで実行に記録する | なし |
| 9 | ワーカーが異常終了した実行の扱い | ジョブの実行基盤が出す「確保していたジョブを失敗にした」という通知を受けて、対応する実行を失敗にする | なし |

判断 3 と判断 5 は組になっている。ジョブを別のプロセスで動かすと、開発環境の Action Cable（`config/cable.yml` の `async`。プロセス内で完結する方式）では、ジョブからの配信が Web のプロセスに届かない。

### 2.2 結合評価サマリ

| # | 起点 → 終点 | 強さ | 距離 | 均衡 | 備考 |
|---|-----------|------|------|------|------|
| 1 | 代表シナリオの処理 → RubyLLM の公開 API | Contract(1) | 異システム(4) | OK | 公開された API だけを使う |
| 2 | `Observability::RubyLLMSpanSubscriber` → RubyLLM の計装イベント | Contract(1) | 異システム(4) | OK | 文書化されたイベントの payload に依存する |
| 3 | 実行のジョブ → 代表シナリオの処理 | Contract(1) | 同一コンテキスト(2) | OK | 入力を渡し、結果を受け取る |
| 4 | 実行のジョブ → OpenTelemetry の API | Contract(1) | 異システム(4) | OK | 現在のトレース ID を読むだけである。Sentry には依存しない |
| 5 | 実行の表示 → Sentry の画面の URL | Contract(1) | 異システム(4) | OK | URL の組み立ては 1 か所に置く |
| 6 | 実行できる状態かどうかの判定 → RubyLLM の公開 API | Contract(1) | 異システム(4) | OK | 必要な設定値の名前の問い合わせと、設定値の読み出しを使う。理由は下 |
| 7 | 異常終了した実行の扱い → ジョブの実行基盤の通知 | Contract(1) | 異システム(4) | OK | Solid Queue が、独自の復旧のために文書で案内している通知を使う |
| 8 | 会話 ID の発行 ⇔ `Observability::RubyLLMSpanSubscriber`（共有知識: 会話 ID に使える文字） | Functional(3) | 同一コンテキスト(2) | △ | 許容する。理由は下 |
| 9 | 失敗の原因の候補 ⇔ `bin/check_keys`（共有知識: エラーの種類と原因の対応） | Functional(3) | 同一コンテキスト(2) | OK | 設計改善で解消した |

**許容している不均衡**: 8 番。会話 ID に使える文字は、Sentry が会話 ID を URL の一部に使うことから決まる規則であり、変わる見込みが低い。発行する側が規則を満たす ID を作り、購読者の側の置換は、規則を満たさない ID が渡された場合の防御として残す。

**設計改善の経緯**:

- 6 番は、当初、RubyLLM がプロバイダーごとに持つ「設定値がそろっているか」の問い合わせを使う設計だった。この問い合わせは RubyLLM 2.0.0 で非公開の扱いである。一方、「必要な設定値の名前」の問い合わせと、プロバイダーの一覧は公開されている。必要な設定値の名前を公開の問い合わせで得て、その値が空でないことをアプリの側で確かめる設計に改めた。設定値の名前をアプリの側に写して持つことはしない。
- 9 番は、当初、エラーの種類から原因の候補を引く対応表を、実行の失敗の記録と `bin/check_keys` の両方が持つ設計だった。対応表を Rails に依存しない 1 か所に置き、両方がそれを使う設計に改めた。`bin/check_keys` は Rails を起動せずに動くため、置き場所は Rails なしで読み込める場所にする。

## 3. データ要件

### 3.1 静的な定義

DB には保持しない。

#### 3.1.1 デモ定義

| 項目 | 必須 | 説明 |
|------|------|------|
| 識別子 | ○ | URL に使う。10 機能に 1 つずつ |
| 表示の順序 | ○ | 要件定義書の機能の並び順 |
| 機能名 | ○ | 依頼の原文の名称。RubyLLM の公式ドキュメントでの名称が異なる場合は、それも持つ |
| 役立つケースの要約 | ○ | 一覧に出す 1 文 |
| 役立つケース | 説明を書いたら ○ | C2 の説明文 |
| 使わない場合に困ること | 説明を書いたら ○ | C2 の説明文。その機能なしで同じ目的を果たそうとしたときの手間と問題を書く |
| 出典 | ○ | 1 件以上。表示名と URL。RubyLLM の公式ドキュメントを含める。プロバイダーの仕様に基づく説明では、プロバイダーの公式ドキュメントも含める |

役立つケースと使わない場合に困ることは、その機能の代表シナリオを実装するときに、公式ドキュメントと gem のソースに照らして書く。この設計で本文を書くのは F1 だけである。ほかの 9 機能は、役立つケースの要約と、RubyLLM の公式ドキュメントの出典だけを持つ。2 つの説明は、両方あるか、両方ないかのどちらかにする。

#### 3.1.2 代表シナリオ定義

| 項目 | 必須 | 説明 |
|------|------|------|
| 識別子 | ○ | 実行から参照する |
| 属するデモ | ○ | デモ定義の識別子 |
| 名称 | ○ | 1 つのデモに代表シナリオが 2 つある場合に区別する |
| 必要なプロバイダー | 実装済みなら ○ | 1 つ以上。要件定義書 3.2 の対応表に従う |
| 使うモデル | 実装済みなら ○ | 1 つ以上。役割（主、予備）を区別できる形で持つ |
| 入力の項目 | 実装済みなら ○ | 項目ごとに、名前、既定値、必須かどうか。要件定義書 2.4 に従う |
| 実行を担う処理 | | 未実装の代表シナリオでは空にする |
| 結果の種類 | 実装済みなら ○ | 結果の表示に使う部品を決める |
| やり直してよいか | 実装済みなら ○ | ジョブが再び実行されたときに、最初からやり直してよいか。5.1.2 で使う |

実行を担う処理が空の代表シナリオは、「準備中」として扱う。10 機能ぶんのデモ定義は最初からそろえ、代表シナリオの処理は機能ごとに足していく。準備中の代表シナリオの入力の項目やモデルは、その機能の設計で決める。

### 3.2 実行

#### 3.2.1 実行

**テーブル名**: `demo_runs`（新規）

| 項目名 | キー | データ型 | 必須 | 説明 |
|--------|------|----------|------|------|
| id | PK | bigint | ○ | 主キー |
| scenario_key | | string | ○ | 代表シナリオ定義の識別子 |
| status | | string | ○ | 状態。実行中、承認待ち、成功、失敗、取り消しのいずれか |
| input | | json | ○ | 実行に使った入力。入力の項目ごとの値 |
| result | | json | | 結果。形は結果の種類ごとに決まる |
| failure | | json | | 失敗の内容。プロバイダー名、エラーの種類、プロバイダーが返したメッセージ、原因の候補 |
| conversation_id | UK | string | ○ | 会話 ID。実行ごとに発行する |
| trace_ids | | json | ○ | トレース ID の配列。既定は空 |
| finished_at | | datetime | | 状態が成功、失敗、取り消しになった日時 |
| created_at | | datetime | ○ | 実行日時。利用者が実行を指示した日時 |
| updated_at | | datetime | ○ | 更新日時 |

**制約**:
- UNIQUE KEY(conversation_id)
- 代表シナリオ定義は DB にないため、scenario_key に外部キーは張らない

**目的**:
- すべての実行を履歴として保持する（C8）
- 失敗した実行も、失敗の内容とともに残す（C8、C10）
- 履歴から Sentry の会話とトレースへ移動する手がかりを持つ（C8）

**データ作成/更新タイミング**:
- 利用者が実行を指示したときに、状態「実行中」で作成する
- ジョブが workflow を開いた直後に、トレース ID を trace_ids に追加する
- ジョブが代表シナリオを終えたときに、結果か失敗の内容、状態、終了日時を更新する
- ジョブの実行基盤が、ワーカーの異常終了でジョブを失敗にしたときに、失敗の内容、状態、終了日時を更新する

トレース ID を配列で持つのは、結果が後から届く機能で、1 回の実行が投入と結果の回収とで複数のトレースに分かれるためである。ジョブがやり直された場合も、トレース ID が増える。

代表シナリオ定義から識別子が消えた実行は、履歴に残す。

#### 3.2.2 生成物

生成した音声と動画は、Active Storage の添付として実行に持たせる。この設計では関連を用意するだけで、F1 は使わない。

### 3.3 既存のデータとの関係

`ruby_llm:install` が作る `chats`、`messages`、`ruby_llm_models`、`ruby_llm_tool_calls`、`ruby_llm_usages`、`ruby_llm_batches` は、この設計では導入だけを行う。F1 は会話を永続化しないため、実行からこれらへの参照は持たない。会話を永続化する機能の設計で、実行との関連を定める。

## 5. ビジネスルール

### 5.1 実行の状態

#### 5.1.1 状態の遷移

- **実行中から**: 承認待ち、成功、失敗、取り消しへ遷移できる
- **承認待ちから**: 実行中、失敗、取り消しへ遷移できる
- **成功、失敗、取り消しから**: 遷移できない
- **目的**: 終わった実行の結果が、後から書き換わらないようにする
- **補足**: この設計で使う遷移は、実行中から成功と、実行中から失敗である。承認待ちと取り消しは、それを使う機能の設計で使う

#### 5.1.2 ジョブが再び実行された場合

ジョブの実行基盤は、ワーカーが正常に停止した場合（再起動など）に、処理の途中だったジョブを待ち行列に戻し、再び実行する。

- **終わった実行**: 何もしない
- **実行中のままの実行で、代表シナリオがやり直してよいもの**: 代表シナリオを最初からやり直す。プロバイダーの呼び出しがもう一度行われ、費用がもう一度かかる
- **実行中のままの実行で、代表シナリオがやり直してはならないもの**: やり直さない。扱いは、その機能の設計で定める
- **やり直してよい代表シナリオ**: 結果がすぐに得られ、取り消せない操作を含まないもの。F1 はやり直してよい
- **やり直してはならない代表シナリオ**: プロバイダー側に処理を投入するもの（F4、F6b、F8）と、取り消せない操作を含むもの（F3）。やり直すと、投入が二重になり、または取り消せない操作がもう一度行われる

#### 5.1.3 ワーカーが異常終了した場合

ジョブの実行基盤（Solid Queue）は、ワーカーが異常終了した場合に、そのワーカーが確保していたジョブを失敗として記録し、自動では再び実行しない。ジョブ自体がワーカーを止めている場合に、繰り返し止めないためである。

- **規則**: ジョブの実行基盤が出す「確保していたジョブを失敗にした」という通知を受けて、対応する実行のうち状態が「実行中」のものを「失敗」にする
- **失敗の内容**: エラーの種類を「ワーカーの異常終了」とし、原因の候補に、ワーカーが止まったことと、もう一度実行すればよいことを示す
- **目的**: 実行が「実行中」のまま残らないようにする

#### 5.1.4 失敗の扱い

- **プロバイダーの呼び出しの失敗にあたるもの**: RubyLLM のエラー、設定値の不足、モデルが見つからないこと、タイムアウトと接続の失敗。後の 3 つは、RubyLLM のエラーの共通の親を継承していないため、別に扱う
- **プロバイダーの呼び出しの失敗**: 実行を「失敗」にして、失敗の内容を記録する。ジョブとしては正常に終える。ジョブの再試行はしない
- **想定していない例外**: 実行を「失敗」にして、例外の種類とメッセージを失敗の内容に記録する。あわせて、エラーの通知の仕組みに報告する。ジョブの再試行はしない
- **目的**: ジョブの再試行は、プロバイダーの呼び出しを繰り返し、費用を増やす
- **RubyLLM 自身の再試行**: RubyLLM は、タイムアウト、接続の失敗、レート制限、サーバー側のエラーを、既定で 3 回まで自動で再試行する。1 回の実行で、プロバイダーの呼び出しが最大 4 回になる。この設計では、既定のままにする。再試行の 1 回ごとは、Sentry のトレースで試行として確認できる

### 5.2 実行できる状態かどうかの判定

#### 5.2.1 代表シナリオの判定

判定の単位は代表シナリオである。1 つのデモの中で、代表シナリオごとに必要なプロバイダーが違う場合があるためである。

- **準備中**: 実行を担う処理が空である
- **設定値が足りない**: 必要なプロバイダーのうち、必要な設定値が空のものがある。足りないプロバイダーの名前を持つ
- **実行できる**: 上のどちらでもない
- **必要な設定値**: RubyLLM の公開の問い合わせで、プロバイダーごとに得る。RubyLLM の設定から、その値が空でないことを確かめる
- **判定しないこと**: 設定値が有効かどうかと、Vertex AI の Application Default Credentials があるかどうか。どちらも、実行したときの失敗の内容で分かる（C10）

#### 5.2.2 デモの一覧に示す値

デモに属する代表シナリオの判定を、次の順でまとめる。

1. 実行できる代表シナリオが 1 つ以上ある場合は「実行できる」
2. そうでなく、設定値が足りない代表シナリオが 1 つ以上ある場合は「設定値が足りない」
3. それ以外は「準備中」

### 5.3 会話 ID

会話 ID は、Sentry が、複数のトレースにまたがる 1 つのやり取りをまとめるために使う識別子である。トレース ID は OpenTelemetry が発行し、1 回の処理の流れを表す。1 つの実行は、1 つの会話 ID と、1 つ以上のトレース ID を持つ。

#### 5.3.1 発行の規則

- **形式**: 英数字、ハイフン、アンダースコアだけからなる、短く、推測できない文字列
- **目的**: Sentry は会話 ID を URL の一部に使う。スラッシュを含む ID は、会話の画面を壊す
- **渡し方**: ジョブが開く workflow の metadata に入れる。workflow の内側で発行される計装イベントのすべてに、この値が載る
- **前提**: 代表シナリオの処理は、必ず workflow の内側で呼ぶ。外側で呼ぶと、スパンに会話 ID が付かない

### 5.4 失敗の原因の候補

#### 5.4.1 エラーの種類と原因の候補の対応

| エラーの種類 | 原因の候補 |
|-------------|-----------|
| 認証の失敗 | 認証情報の誤りか失効。Vertex AI では Application Default Credentials の失効 |
| 不正なリクエスト | リクエストの内容の誤り。xAI は、無効な認証情報もこの種類で返す |
| 支払いが必要 | 残高の不足 |
| レート制限 | レート制限か、残高の不足。OpenAI は、残高の不足もこの種類で返す |
| 権限の不足 | モデルへのアクセス権、API の有効化、権限の設定 |
| 設定値の不足 | 環境変数の未設定か、変数名の誤り |
| モデルが見つからない | モデルの識別子の誤り |
| 入力がモデルの上限を超えた | 入力がモデルの上限を超えている。入力を短くする |
| サーバー側のエラー、過負荷、サービス停止 | プロバイダー側の障害。時間をおいて実行する |
| タイムアウト、接続の失敗 | ネットワークか、プロバイダー側の障害 |
| ワーカーの異常終了 | ジョブのワーカーが止まった。もう一度実行する |

- **置き場所**: この対応は 1 か所に置き、実行の失敗の記録と `bin/check_keys` の両方が使う
- **この表にないエラー**: 原因の候補を空にして、エラーの種類とメッセージだけを示す

### 5.5 入力

#### 5.5.1 入力の規則

- **必須の入力の項目**: 1 つでも空の場合は、実行を記録しない
- **長さ**: 上限を設けない。モデルの上限を超えた場合は、プロバイダーの呼び出しの失敗として、C10 のとおり示す
- **同時の実行**: 同じ代表シナリオの実行を、同時に複数記録することを妨げない。実行のたびに、プロバイダーの呼び出しと費用が発生する。利用者は 1 人で、ローカルで実行するためである
- **入力の内容**: 入力の本文は Sentry に送られる。実データと個人情報を入れてはならない（要件定義書 3.2）

### 5.6 F1 の代表シナリオ

#### 5.6.1 入力と結果

- **入力の項目**: 顧客からの問い合わせ文。必須。既定値は、架空の EC サイトへの問い合わせである
- **使うモデル**: OpenAI のテキスト生成のモデル。RubyLLM が Responses API を既定のプロトコルにするモデルから選ぶ。音声、リアルタイム、検索用のモデルは、Chat Completions で送信されるため、選ばない
- **処理**: サポートデスクの担当者として回答するよう指示を与え、回答を得る。プロトコルは指定せず、RubyLLM の既定に任せる。Web 検索は使わない
- **結果**: 回答の本文と、応答したモデルの名前
- **結果の種類**: テキストの回答
- **やり直してよいか**: よい
- **確認の方法**: Responses API で送信されたことは、Sentry のトレースにある、プロバイダーへのリクエストのスパンの送信先で確認する。アプリの画面には出さない

## 6. 画面表示機能

### 6.1 デモの一覧

#### 6.1.1 画面レイアウト
- **デモの並び**: 10 機能を、表示の順序に従って並べる。機能名を主内容、役立つケースの要約を副内容とする
- **実行できる状態かどうか**: デモごとに、5.2.2 の値を示す。「設定値が足りない」場合は、足りないプロバイダーの名前を添える
- **共通の案内**: 履歴の一覧への移動を、どの画面にも置く

#### 6.1.2 アクション一覧
| アクション | 順位 | 説明 |
|-----------|------|------|
| デモを開く | 主 | 選んだデモの画面へ移動する |
| 履歴を開く | 副 | 履歴の一覧へ移動する |

#### 6.1.3 画面状態
| 状態 | 表示・挙動 |
|------|-----------|
| 空 | 該当しない。デモ定義は常に 10 件ある |
| ロード中 | 待たせる操作はない |
| エラー | 失敗しうる操作はない |

### 6.2 デモの画面

#### 6.2.1 画面レイアウト
- **説明**: 役立つケースを主内容、使わない場合に困ることを副内容とする。見出しで 2 つを区別する
- **出典**: 説明の直後に置く。表示名を示し、別の画面で開く
- **代表シナリオ**: 代表シナリオごとに、名称、コード断片、入力欄、実行の指示をひとまとまりにする。入力欄には、既定値を入れておく。実行の画面から入力を持ち越して開いた場合は、その入力を入れておく
- **入力についての注意**: 入力欄のそばに、副内容として示す。入力の本文が Sentry に送られることと、実データと個人情報を入れないこと
- **このデモの最近の実行**: 代表シナリオの下に置く。状態と実行日時を示し、実行の画面へ移動できる。示す件数は未定である

#### 6.2.2 アクション一覧
| アクション | 順位 | 説明 |
|-----------|------|------|
| 実行する | 主 | 代表シナリオごとに 1 つ。実行を記録して、実行の画面へ移動する |
| 入力を既定に戻す | 副 | 変更した入力を既定値に戻す |
| 最近の実行を開く | 副 | 実行の画面へ移動する |
| 出典を開く | 従 | 公式ドキュメントを別の画面で開く |

代表シナリオが 2 つあるデモでは、「実行する」が 2 つ並ぶ。どちらも、その代表シナリオのまとまりの中では 1 つだけの主アクションである。

#### 6.2.3 画面状態

代表シナリオのまとまりごとの状態である。

| 状態 | 表示・挙動 |
|------|-----------|
| 実行できる | 入力欄と「実行する」を出す |
| 設定値が足りない | 「実行する」を押せない状態にする。足りないプロバイダーの名前と、取得手順の文書（`docs/api-keys.md`）と疎通確認の手順（`bin/check_keys`）の場所を示す（C11） |
| 準備中 | 「実行する」とコード断片と入力欄を出さず、準備中であることを示す |
| 最近の実行が 0 件 | まだ実行がないことを示す。追加の誘導はしない。主アクションが同じ画面にある |
| 説明がない | 役立つケースの要約と出典を示し、説明はこの機能の代表シナリオとあわせて用意することを示す |
| ロード中 | 「実行する」の後は、すぐに実行の画面へ移動する。この画面では待たせない |
| エラー | 実行の指示が受け付けられなかった場合は、実行を記録せず、理由を示す。必須の入力の項目が空の場合は、その入力欄のそばに示す。画面を開いた後で実行できる状態でなくなった場合は、代表シナリオのまとまりに示す |

出典は、どの状態でも出す。説明は、書かれていればどの状態でも出す。

### 6.3 実行の画面

#### 6.3.1 画面レイアウト
- **状態**: 主内容。5 つの状態のどれかを、文字で示す
- **結果**: 状態が成功のときの主内容。結果の種類ごとの部品で示す。F1 では、回答の本文を主内容、応答したモデルの名前を副内容とする
- **失敗の内容**: 状態が失敗のときの主内容。エラーの種類とプロバイダー名を主内容、プロバイダーが返したメッセージと原因の候補を副内容とする
- **入力**: 副内容。実行に使った入力をそのまま示す
- **実行の情報**: 副内容。デモと代表シナリオの名称、実行日時、終了日時
- **Sentry への移動**: トレースごとのリンクと、会話へのリンク

#### 6.3.2 アクション一覧
| アクション | 順位 | 説明 |
|-----------|------|------|
| Sentry でトレースを開く | 主 | 観察情報を確認する。トレースが複数ある場合は、新しいものを主とし、残りを副とする |
| Sentry で会話を開く | 副 | 会話の画面を開く |
| この入力でデモを開く | 副 | この実行の入力を持ち越して、デモの画面へ移動する。そのまま実行すれば同じ入力での再実行になり、変更してから実行すれば入力を変えた再実行になる（C6） |
| デモに戻る | 副 | この実行の代表シナリオが属するデモの画面へ移動する。入力は持ち越さない |

#### 6.3.3 画面状態
| 状態 | 表示・挙動 |
|------|-----------|
| 実行中 | 実行中であることと、実行を指示してからの経過を示す。状態を短い間隔で取得し直す。進まない場合に備えて、ジョブのワーカーが動いているかを確かめるよう、案内を添える |
| 成功 | 結果を示す。取得をやめる |
| 失敗 | 失敗の内容を示す。取得をやめる |
| 承認待ち、取り消し | 状態だけを示す。操作は、それを使う機能の設計で定める |
| トレース ID がない | Sentry でトレースを開く操作を出さない。会話を開く操作は出す |
| 代表シナリオ定義がない実行 | 代表シナリオの名称の代わりに、識別子を示す。「この入力でデモを開く」と「デモに戻る」を出さない |
| 状態の取得の失敗 | 表示は変えず、次の間隔でもう一度取得する。利用者は、画面の再読み込みでも復帰できる |
| 存在しない実行 | 実行が見つからないことを示し、履歴の一覧へ誘導する |
| 極端なデータ | 長い回答と長い入力は、折り返して全文を示す。省略はしない |

状態を取得し直す間隔の値は、実装で決める。

Sentry の画面の URL は、利用者の Sentry の画面で確かめた次の形式にする。

- **トレース**: `https://<組織の識別子>.sentry.io/explore/traces/trace/<トレース ID>/`
- **会話**: `https://<組織の識別子>.sentry.io/explore/agents/conversations/<会話 ID>/`
- **共通の問い合わせ**: プロジェクトの ID と、実行日時の前後を含む期間。画面内の選択状態を表す値は付けない

組織の識別子は DSN に含まれないため、設定値として持つ。プロジェクトの ID は DSN から得る。

### 6.4 履歴の一覧

#### 6.4.1 画面レイアウト
- **実行の並び**: 新しい順。デモと代表シナリオの名称を主内容、状態と実行日時を副内容とする
- **絞り込み**: デモで絞り込める。代表シナリオ定義がない実行は、絞り込みをしていないときだけ出る
- **件数が多い場合**: ページに分ける。1 ページの件数は未定である

#### 6.4.2 アクション一覧
| アクション | 順位 | 説明 |
|-----------|------|------|
| 実行を開く | 主 | 実行の画面へ移動する |
| デモで絞り込む | 副 | 選んだデモの実行だけを示す |

#### 6.4.3 画面状態
| 状態 | 表示・挙動 |
|------|-----------|
| 空（0 件） | まだ実行がないことを示し、デモの一覧へ誘導する |
| 絞り込みの結果が 0 件 | そのデモの実行がないことを示し、そのデモの画面へ誘導する |
| ロード中 | 待たせる操作はない |
| エラー | 失敗しうる操作はない |

### 6.5 要件に明記のない表示と操作

次のものは、要件定義書に明記がない。C8 の「後から見返せる」と、C6 の「入力ごとの結果を履歴で見比べる」を満たすために加えた。

- 履歴の一覧の、デモでの絞り込みと、ページ分け
- デモの画面の、このデモの最近の実行
- 実行の画面の、この入力でデモを開く操作

### 6.6 エラーハンドリング

#### 6.6.1 エラー分類
| エラーレベル | 説明 | 処理継続 |
|-------------|------|----------|
| ERROR | プロバイダーの呼び出しの失敗。実行を失敗にして、失敗の内容を示す | その実行は中止。アプリは継続 |
| ERROR | 想定していない例外。実行を失敗にして、エラーの通知の仕組みに報告する | その実行は中止。アプリは継続 |
| ERROR | ワーカーの異常終了。実行を失敗にする | その実行は中止。アプリは継続 |
| WARNING | 計装の失敗。スパンを作れなくても、代表シナリオの実行は続ける | 継続 |
| WARNING | 実行の指示が受け付けられない。必須の入力の項目が空、実行できる状態でない、代表シナリオが存在しない、のいずれか。実行を記録しない | 継続 |

計装の失敗で実行を止めないのは、既存の `Observability::RubyLLMSpanSubscriber` の設計である。観察のための処理が、観察の対象であるプロバイダーの呼び出しを失敗させてはならない。

## 7. ログ設計

要件定義書に監査・記録要件はない。エラーの記録の方針だけを定める。

### 7.7 エラー記録方針

- **通知対象例外**: 想定していない例外。プロバイダーの呼び出しの失敗と、ワーカーの異常終了は、実行に記録して画面に示すため、通知の対象にしない
- **コンテキスト**: 実行の ID、代表シナリオの識別子、会話 ID
- **通知の経路**: アプリのコードは、フレームワークのエラー報告の仕組みだけを使う。エラーの監視の SDK を直接は呼ばない
- **テスト環境**: 通知も計装も行わない。テスト環境でも、実際の DSN が環境変数として読み込まれるためである

## 8. 環境構築と前提

要件定義書 4.1 への追加は次のとおり。

- **ジョブの実行基盤**: 開発環境で、Active Job の実行基盤を、ジョブを DB に保持する方式（Solid Queue）にし、ジョブ用の DB へ接続する。現状は、この 2 つの指定が `config/environments/production.rb` にだけある。開発環境は、Web のプロセスの中でジョブを動かす既定のままである
- **開発環境の DB**: ジョブ用の DB を、開発環境にも設ける。現状の `config/database.yml` は、ジョブ用の DB を本番環境にだけ定義している
- **ワーカーの起動**: 既存の `config/puma.rb` は、環境変数 `SOLID_QUEUE_IN_PUMA` があるときに、Puma からワーカーを起動する。ワーカーは、Web のプロセスとは別のプロセスで動く。開発用の起動の手順で、これを有効にする
- **ジョブの前提**: 代表シナリオの実行は、ワーカーが動いていることを前提とする。動いていない間の実行は、「実行中」のまま待つ
- **RubyLLM の Rails 統合**: `ruby_llm:install` を実行する。このジェネレーターは `config/initializers/ruby_llm.rb` も生成しようとする。既存のファイルと衝突するため、既存の内容を残す。モデルの一覧を DB に読み込む
- **Active Storage**: `ruby_llm:install` が導入する
- **スタイリング**: Tailwind を導入する。開発用の起動の手順で、CSS のビルドを同時に動かす
- **設定値**: Sentry の組織の識別子を追加する
- **自動テスト**: 対象は、外部の API を呼ばない部分に限る（要件定義書 3.2）。実行できる状態かどうかの判定、状態の遷移、ジョブが再び実行された場合の分岐、失敗の原因の候補の対応、画面の表示である。プロバイダーの呼び出しは、実際の画面で確かめる

# ChangeSpec: 実行の画面で Sentry へのリンクを結果より前に置く

## 変更の目的

実行の画面で、Sentry へのリンク（「Sentry でトレースを開く」「Sentry で会話を開く」「以前のトレース N」）が結果の表示の下にあり、F3 と F10 のように結果が長い実行では、画面を開いた時点で目に入らず、スクロールしないと見つからない。観察情報の確認手段は Sentry だけ（要件定義書の C7、C8）なので、リンクを結果の長さによらず画面の上部に置く。F10 の実装時に次のフェーズへ回し、F3 の実装時に別の ChangeSpec で扱うと決めた項目である。

## 現状

実行の画面 `app/views/runs/show.html.erb` は、ヘッダー（デモ名、代表シナリオ名）、拒否された決定の理由、状態で変わる部分、入力、デモへのリンクの順に描画する。

状態で変わる部分 `app/views/runs/_details.html.erb` は、次の順に描画する。

1. 状態のバッジ（大）。実行中なら、実行を指示してからの経過秒数と、ジョブのワーカーの注意書き。バッジと経過秒数の行は折り返さない
2. 承認待ちなら、承認の要求と「承認する」（`btn-primary`）「却下する」（`btn-secondary`）のボタン。決定の済んだ要求には決定を表示し、ボタンを出さない
3. 成功なら、代表シナリオ定義の `result_kind` と同じ名前の結果の表示部品。代表シナリオの定義が消えた実行では `raw`（結果をそのまま表示する）
4. 失敗なら、失敗の内容（種類、プロバイダー、メッセージ、原因の候補）
5. Sentry へのリンク。組織名（`SENTRY_ORG`）があり、DSN（`SENTRY_DSN`）からプロジェクト ID が取れるとき、最新のトレースを「Sentry でトレースを開く」（`btn-primary`）、会話を「Sentry で会話を開く」、それより古いトレースを「以前のトレース N」（どちらも `btn-secondary`）として横に並べる。トレースが記録されていなければ会話のリンクだけを出す。組織名か DSN が使えなければ、`.env` に 2 つの値が要るという説明を出す
6. 実行日時と終了日時

承認の要求（`data-approval`）、失敗の内容（`data-failure`）、F3 と F10 の結果の表示部品（`data-refund-decision`、`data-ticket-workflow`）には目印の属性があるが、状態の行、Sentry へのリンクのまとまり、F1 の結果の表示部品（`text_answer`）と `raw` にはない。

この部分は、実行中のあいだ Stimulus の `poll` コントローラーが、状態の取得（`Runs::StatusesController`）の応答で要素ごと置き換える。トレース ID は、ジョブが workflow の内側で `Demos::Run#add_trace_id!` で記録するため、実行中に増える。F3 のように承認で再開する実行では、ジョブが動くたびに 1 つ増える。リンクがこの部分にあるのは、記録され次第、置き換えで画面に出るようにするためである。

結果の表示部品は `max-w-prose` の幅で縦に並ぶ。F10（分類、回答の下書き、レビュー）と F3（返金の提案、注文の状態、顧客への回答）の結果は 1 画面に収まらない長さになり、F1 の回答も数段落になる。

リンクの URL は `RunsHelper#sentry_trace_url`（時刻は `started_at`、なければ `created_at`）と `RunsHelper#sentry_conversation_url`（`created_at` から `finished_at` または現在まで）が、`Observability::SentryLinks` で組み立てる。`SentryLinks.from_env` は環境変数を直接読む。テスト環境でも dotenv が `.env` を読むため、開発者の `.env` に Sentry の値があるかどうかで、テストの結果が変わる。画面のテストは `ScreenHelpers#with_env` で環境変数を固定して、この依存を断つ。

テストは `test/controllers/runs_controller_test.rb` に、Sentry の値を固定したうえで、最新のトレースが `btn-primary`、以前のトレースが `btn-secondary`、会話のリンクがあること、トレースがなければ会話のリンクだけがあること、の検証がある。設定がないときの説明の検証はない。`test/controllers/runs/statuses_controller_test.rb` は、状態の取得が状態のバッジ、結果、承認の要求を返し、ページ全体ではないことを検証する。`test/controllers/runs/decisions_controller_test.rb` は、拒否のときに描画される実行の画面を、拒否の理由と承認の要求の目印で検証する。いずれの検証も、画面内の位置に依存しない。

## 変更内容

- **変更**: 状態で変わる部分の描画の順序。Sentry へのリンク（設定が使えないときの説明を含む）を、状態のバッジと同じ行に置く。バッジと経過秒数を左に、リンクを右端に寄せる。行は折り返し、幅が足りなければ、リンクはバッジの下に回る。ワーカーの注意書きは、この行の下に残す。承認の要求、結果、失敗の内容、日時の順序は変えない。リンクの文言と URL は変えない
- **変更**: 承認待ちのあいだは、Sentry へのリンクをすべて `btn-secondary` にする。承認待ちでは「承認する」が主アクションで、その上に `btn-primary` の「Sentry でトレースを開く」が並ぶと、主アクションの見た目が 2 つになるためである。承認待ち以外の状態では、現状どおり最新のトレースだけを `btn-primary` にする
- **追加**: 順序を検証するための目印。Sentry へのリンクのまとまり（説明で代える場合を含む）に `data-sentry-links`、結果の表示部品を描画する枠に `data-run-result` を付ける。順序の検証は、この目印と既存の目印（`data-approval`、`data-failure`）の文書内の位置を比べる
- リンクは状態で変わる部分に留める。ページのヘッダーに出すと、実行中に記録されたトレース ID が、利用者が再読み込みするまで出ないためである

描画の順序は次のとおり変わる。

| 順 | 変更前 | 変更後 |
|----|--------|--------|
| 1 | 状態のバッジ、経過秒数、ワーカーの注意書き | 状態のバッジ、経過秒数、Sentry へのリンク（同じ行、右端）。その下にワーカーの注意書き |
| 2 | 承認の要求 | 承認の要求 |
| 3 | 結果の表示部品 | 結果の表示部品（`data-run-result` の枠の内側） |
| 4 | 失敗の内容 | 失敗の内容 |
| 5 | Sentry へのリンク | （なし） |
| 6 | 実行日時、終了日時 | 実行日時、終了日時 |

承認待ちの実行では、リンクの行が承認の要求より上に来る。リンクの行は、幅が足りれば 1 行で、以前のトレースが増えれば折り返して 2 行以上になる。承認の要求はその直下に出るため、決定のボタンは画面を開いた時点で目に入る。

新規に追加する責務はない。結合強度評価は省略する（表示の順序と見た目の変更で、既存の結合点に触れない）。使い勝手の点検は、この変更自体が F10 と F3 の実装後に画面を見て見つかった指摘への対応であるため、承認待ちの主アクションとの競合の点検だけを行い（上の 2 つ目の変更）、それ以外は省略する（自習用のデモで、操作者は利用者本人である）。

このリポジトリでは ADR を起票しない（利用者の決定）。採用案と理由だけを記す。

| # | 判断ポイント | 採用案 | 関連 ADR |
|---|------------|--------|---------|
| 1 | リンクの置き場所（状態のバッジの行、ページのヘッダー、画面に固定したバー） | 状態のバッジの行。状態で変わる部分に留まるので、実行中に記録されたトレース ID がポーリングの置き換えで出る。ページのヘッダーは置き換えの対象外で、再読み込みまで出ない。画面に固定したバーは共通レイアウトの変更になり、この問題に対しては大きすぎる | なし |
| 2 | 承認待ちのときの主アクションの見た目（承認待ちだけリンクを `btn-secondary` にする、常にリンクを `btn-secondary` にする、両方 `btn-primary` のままにする） | 承認待ちだけ `btn-secondary` にする。終了した実行では Sentry のトレースが確認の主な手段なので、リンクの `btn-primary` は残す。常に `btn-secondary` にすると、最新のトレースと以前のトレースの区別が文言だけになり、既存の検証も変わる | なし |

- 実装済みの結果の表示部品（F1、F3、F10、`raw`）と、これから加える表示部品（F9a、F6a、F7a）は、`data-run-result` の枠の内側の同じ位置に描画される。変更しない
- テスト。Sentry の値は `with_env` で固定する（リンクを出す検証では架空の組織名と DSN を、説明を出す検証では空を入れる）。テスト環境でも dotenv が開発者の `.env` を読むためである
  - `test/controllers/runs_controller_test.rb`: 成功した F10 と F3 の実行、承認待ちの実行、失敗した実行、実行中の実行で、リンクのまとまりが結果の枠、承認の要求、失敗の内容より文書の順序で先にあることの検証。承認待ちの実行でリンクがすべて `btn-secondary` で「承認する」だけが `btn-primary` であることの検証。設定が使えないときに説明が状態の行に出ることの検証。既存の検証は位置に依存しないので変えない
  - `test/controllers/runs/statuses_controller_test.rb`: 状態の取得の応答で、リンクのまとまりが結果の枠より先にあることの検証

## 受け入れ条件

表示の順序と見た目の調整なので、箇条書きで書く。すべてテストで検証する。「先にある」は、文書の順序で先にあることを指し、目印の属性の位置で確かめる。

- 成功した F10 の実行と F3 の実行の画面で、Sentry の設定があるとき、リンクのまとまりが結果の枠より先にあり、「Sentry でトレースを開く」が `btn-primary` である
- 承認待ちの実行の画面で、リンクのまとまりが承認の要求より先にあり、リンクはすべて `btn-secondary` で、`btn-primary` は「承認する」だけである。「却下する」も引き続き表示される
- 失敗した実行の画面で、リンクのまとまりが失敗の内容より先にある
- 実行中の実行の画面で、状態のバッジ、経過秒数、ワーカーの注意書き、リンクのまとまり（トレースがなければ会話のリンクだけ）が表示され、ポーリングは続く
- Sentry の設定が使えないとき、`.env` の説明がリンクのまとまりとして状態の行に出る
- 状態の取得の応答で、リンクのまとまりが結果の枠より先にある
- 既存の検証（最新のトレースが `btn-primary`、以前のトレースが `btn-secondary`、会話のリンクがある。トレースがなければ会話のリンクだけ）が変更なしで通る

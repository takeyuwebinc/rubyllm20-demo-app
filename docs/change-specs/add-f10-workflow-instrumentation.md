# ChangeSpec: F10 Workflow Instrumentation の代表シナリオを追加する

## 変更の目的

要件 F10 の代表シナリオ「チケットの分類、回答の下書き、レビューを順に行う」をデモ基盤に載せ、複数のステップからなる処理のどのステップが時間とコストを使っているかを、Sentry のトレースで確かめられるようにする。あわせて、C2〜C5 が求める説明文、出典、コード断片、既定の入力での実行をそろえる。対応する要件は、要件定義書の F10、C2〜C5、C7 である。

## 現状

デモ定義 `config/demos.yml` の `workflow-instrumentation` は、要約と出典 2 件（Instrumentation and Observability、Agentic Workflows）を持ち、説明文の本文（役立つケース、使わない場合に困ること）を持たない。代表シナリオ `run_ticket_workflow` は実行を担う処理（`handler`）を持たず、一覧とデモの画面で「準備中」と表示される。

実行のジョブ `Demos::RunJob` は、すべての代表シナリオを `RubyLLM.workflow` で包む。workflow の名前はデモ名と代表シナリオ名から作り、`metadata:` に実行の会話 ID を渡す。ジョブは workflow の内側でトレース ID を実行に記録し、`Demos::Scenario#perform` を通じて代表シナリオの処理を呼ぶ。workflow のオブジェクトは代表シナリオの処理に渡さない。

代表シナリオの処理は `ApplicationAction` の下に機能ごとの名前空間で置き、入力とモデルをキーワードで受け取り、結果のハッシュを返し、例外はそのまま投げる。実装済みは F1 の `ResponsesApi::AnswerInquiry` だけである。デモの画面は、この処理のソースファイルをそのままコード断片として表示する。

成功した実行の結果は、代表シナリオの `result_kind` と同じ名前の表示部品 `app/views/runs/results/_<result_kind>.html.erb` が表示する。実装済みは `text_answer` と、代表シナリオの定義が消えた実行のための `raw` である。

購読者 `Observability::RubyLLMSpanSubscriber` は、RubyLLM の計装イベントを OpenTelemetry のスパンにする。`workflow.ruby_llm` は名前 `invoke_agent <workflow 名>` のスパン（`sentry.op` は `gen_ai.invoke_agent`）、`workflow_step.ruby_llm` はステップ名のスパン（`sentry.op` なし。固有の属性はステップ ID だけ）、`chat.ruby_llm` は名前 `chat <モデル>` のスパン（`sentry.op` は `gen_ai.chat`。トークン数、コスト、プロンプトと応答の本文を持つ）になる。request 以外のすべてのスパンには、相関の属性として workflow 名（`gen_ai.agent.name`）と会話 ID（`gen_ai.conversation.id`）を付ける。会話 ID は、各イベントの `workflow_metadata` にある `conversation_id` からだけ取る。属性はスパンを閉じるときにまとめて付けるため、開いている途中のスパンは属性を持たない。

RubyLLM 2.0.0 の workflow の仕様は次のとおりである（gem のソースと実測で確認した）。

- `step` は `RubyLLM::Workflow` のインスタンスのメソッドで、`RubyLLM.workflow`（または `Context#workflow`）のブロックが受け取るオブジェクトで呼ぶ。`RubyLLM` モジュールの関数としては提供されていない
- workflow は入れ子にできる。内側の workflow は自分の ID と名前を持ち、イベントに `workflow_parent_id` を載せる。外側のステップの中で開いた場合は `workflow_parent_step_id` も載せる
- 内側の workflow が `metadata:` を持たないとき、内側で発行されるイベント（workflow、workflow_step、chat、usage、request）は `workflow_metadata` を持たない。外側の metadata は引き継がれない

したがって、代表シナリオの処理が自分で workflow を開くと、現状の購読者では内側の chat スパンに会話 ID が付かず、Sentry の Conversations でその実行の chat が会話にまとまらない。

テストは、カタログ（実装済みの代表シナリオの定義の検証、モデルとプロバイダーの一致）、デモと実行の画面（結合テスト）、実行の指示（必須の入力が空白のときの拒否）、ジョブ（差し替えた処理での成否の記録。結果が保存されないことは確かめていない）、購読者（メモリ上のエクスポーターでスパンを検証）がある。カタログのテストは、実装済みの代表シナリオの `retryable` が nil でないことは確かめるが、値が `true` かどうかは確かめない。既存の画面のテストは「準備中」の例に Citations を使っており、F10 が実行できるようになっても影響を受けない。

## 変更内容

- **追加**: F10 の代表シナリオの処理。サポートチケット 1 件と、使うモデルを受け取り、自分で workflow を開いて 3 つのステップを順に実行し、結果を返す。処理の流れは次のとおり
  1. 名前「サポートチケットへの回答」の workflow を開く。ID は RubyLLM に生成させ、`metadata:` は渡さない
  2. ステップ「分類」で、チケットを 5 つの区分（配送、返品・返金、商品の不具合、支払い、その他）のいずれかに分類する。構造化出力で、区分と分類の理由を得る
  3. ステップ「回答の下書き」で、区分とチケットを踏まえた、サポートデスクの担当者としての回答文を得る
  4. ステップ「レビュー」で、下書きをチケットと区分に照らして点検し、構造化出力で判定（合格、要修正のいずれか）と指摘を得る。指摘は、判定が要修正のときは直すべき点で、合格のときは空でよい
  5. 区分、分類の理由、下書き、判定、指摘、応答したモデルを結果として返す
  - 各ステップでモデルを 1 回だけ呼ぶ。ステップの所要時間、トークン数、コストが、そのステップの内側の chat のスパン 1 つと一致するようにするためである
  - 3 つのステップは同じモデル（`gpt-5-nano`）を使う。ステップの違いがトークン数の違いとして見えるようにするためである
  - ジョブが再び実行されたときは最初からやり直してよい（`retryable: true`）。この処理はプロバイダー側に仕事を残さず、取り消せない操作もしない
  - 例外はそのまま投げる。途中のステップで失敗したとき、後続のステップは実行しない
- **追加**: F10 の結果の表示部品（`result_kind` は `ticket_workflow`）。「分類」「回答の下書き」「レビュー」の見出しをステップと同じ名前、同じ順で並べ、区分と理由、下書き、判定と指摘を表示し、末尾に応答したモデルを示す。指摘が空のときは「指摘なし」と示す。見出しをステップ名とそろえるのは、画面の結果と Sentry のトレースのステップを対応づけて読めるようにするためである
- **変更**: デモ定義 `config/demos.yml` の `workflow-instrumentation`
  - 役立つケースの本文。`RubyLLM.workflow` と `step` が、ブロックの内側で発行されるすべての計装イベントに workflow と ステップの ID、名前、タイミングを付けること。処理の流れは通常の Ruby のまま書けること。`metadata:` で実行を識別する値を全イベントに載せられること。workflow を入れ子にすると内側が sub-tree として現れること
  - 使わない場合に困ることの本文。計装イベントがどの処理のどの段階のものか分からず、同じモデルを 3 回呼ぶ処理では chat のイベントを見分けられないこと。段階ごとの所要時間や合計を自分で集計する仕組みと、識別子を呼び出しごとに引き回す仕組みを、自分で書いて保守すること
  - 出典は既存の 2 件（Instrumentation and Observability、Agentic Workflows）を使う。プロバイダーの仕様に基づく説明はないため、プロバイダーの文書は加えない
  - 代表シナリオ `run_ticket_workflow` に、処理、プロバイダー（OpenAI）、モデル（`model: gpt-5-nano`）、入力（`ticket`。サポートチケット。必須。既定値は架空の EC サイトの商品の不具合に関するチケット）、結果の種類（`ticket_workflow`）、やり直しの可否（`true`）を加える
- **変更**: 購読者の会話 ID の取り方。購読者は、`workflow.ruby_llm` のスパンを開くとき、その workflow の会話 ID（`workflow_metadata` の `conversation_id`）を、自分が持つ開いているスパンの記録に控える。各イベントの会話 ID は、イベント自身の `workflow_metadata` にあればそれを使い、なければ、その時点で開いている workflow の記録のうち最も内側で会話 ID を持つものの値を使う。どちらにもなければ、現状どおり会話 ID の属性を付けない。会話 ID に使える文字の置き換えは現状のまま残す

## 結合への影響

| # | 結合点 | 変更前 強さ/距離 | 変更後 強さ/距離 | 備考 |
|---|--------|----------------|----------------|------|
| 1 | F10 の処理 → RubyLLM の公開 API（workflow、step、chat、構造化出力） | なし（新規） | Contract(1)/異システム(4) OK | 公開された API だけを使う。F1 と同じ |
| 2 | F10 の結果の表示 ⇔ F10 の処理（共有知識: 結果の項目名） | なし（新規） | Model(2)/異コンテキスト(3) OK | F1 の `text_answer` と同じ形と距離 |
| 3 | 購読者 → RubyLLM の計装イベント | Contract(1)/異システム(4) OK | Contract(1)/異システム(4) OK | 会話 ID の取り方が変わるだけで、依存するイベントの項目は増えない |
| 4 | ジョブ ⇔ 購読者（共有知識: 会話 ID は workflow の metadata の `conversation_id` にある。変更後は、metadata を持たない内側の workflow がその会話に属することも含む） | Functional(3)/同一コンテキスト(2) △ | Functional(3)/同一コンテキスト(2) △ | 許容。理由は下 |

許容する不均衡は 4 番である。F10 の処理はこの共有知識を持たない。処理は会話 ID を知らず、metadata を渡さない通常の RubyLLM のコードである。引き継ぎの規則は計装の性質として購読者だけが持ち、規則が破れても実行は失敗せず、Sentry での会話のまとまりが崩れるだけである。

## 影響範囲

- `config/demos.yml`: `workflow-instrumentation` の定義。一覧とデモの画面の表示が「準備中」から、OpenAI の設定値の有無に応じて「実行できる」または「設定値が足りない（OpenAI）」に変わる
- 新規: 代表シナリオの処理のファイルと、結果の表示部品のファイル
- `app/subscribers/observability/ruby_llm_span_subscriber.rb`: 会話 ID の取り方
- `app/jobs/demos/run_job.rb`、`app/models/demos/scenario.rb`: 変更なし
- `docs/api-keys.md`: 変更なし。使う認証情報は OpenAI だけで、取得済みである
- Sentry でのトレースの形: F10 の実行のトレースは、ジョブの workflow の `invoke_agent` の下に、処理の workflow の `invoke_agent` が入れ子になり、その下に 3 つのステップのスパンと、各ステップの chat のスパンが並ぶ。Sentry が入れ子の `invoke_agent` をどう表示するか、ステップのスパン（`sentry.op` なし）で所要時間が読めるかは、実装後に画面で確かめる。ステップの所要時間が読めない場合は、ステップのスパンに `sentry.op` を付ける変更を別に検討する
- テスト
  - カタログ: 既存の「実装済みの代表シナリオの定義」の検証が F10 にも及ぶ。F10 の定義（`retryable` が `true`、入力が `ticket` 1 つ）の検証を加える
  - デモの画面: F10 の説明文、出典、コード断片、入力欄、設定値がないときの表示の検証を加える
  - 実行の指示: F10 でチケットが空白のときの拒否の検証を加える
  - 実行の画面: F10 の結果の表示（指摘が空のときを含む）の検証を加える
  - ジョブ: 失敗したとき結果が保存されないことの確認を、既存のテストに加える。あわせて、F10 の処理をジョブで動かし、`RubyLLM.chat` を差し替えて 2 番目のステップで失敗させるテストを加える（プロバイダーは呼ばない）
  - 購読者: 入れ子の workflow への会話 ID の引き継ぎと、閉じた workflow の会話 ID が残らないことの検証を加える
  - 代表シナリオの処理の正常な結果は、プロバイダーを呼ぶためテストしない（要件定義書 3.2 の制約）。実際の画面と Sentry で確かめる

#### 実装後の照合で許容した条件

- metadata の文字列キー `"conversation_id"` も読む: 変更前からある分岐で、この変更の対象外である
- 構造化出力の応答の本文が空だと、`parsed` が nil になり NoMethodError になる。ジョブはこれをアプリの不具合として報告する: strict なスキーマでは起きにくく、起きたときに Sentry のエラーとして見えることが望ましい
- 判定が合格なら緑、それ以外なら amber で表示する: 見た目だけの違いで、判定の文字は常に表示される
- 結果の表示部品の見出しは、処理のステップ名と同じ文字列を持つ: 処理の側を定数にすると、コード断片の `workflow.step("分類")` が読みにくくなる（C4）。判定の値は処理の定数を表示部品が参照する
